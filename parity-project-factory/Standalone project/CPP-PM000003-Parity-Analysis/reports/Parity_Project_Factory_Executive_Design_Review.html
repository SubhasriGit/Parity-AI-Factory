Executive decision

The design is credible and demo-ready, but its strongest value is the separation of deterministic processing, bounded AI assistance, governed human review, and reproducible evidence.

2Core deliverablesReusable factory + CPP implementation
12CPP pipeline tasksDependency-ordered, auditable execution
$0.00In-pipeline model costDeterministic Python boundary; no model API call
0.093415 USD50-case LLM estimateIllustrative, not billed spend

What is proven

  • Factory generates standalone projects from a confirmed JSON specification.
  • Projects retain their own engine, configuration, agents, rules, tests, and evidence.
  • CPP processes 250 synthetic records with zero reconciliation defects.
  • Only unresolved classifications are eligible for LLM review.
  • Retry and review markers remain visible without stopping report generation.

What is not yet proven

  • Production provider contract price and actual invoice token usage.
  • Enterprise-wide daily/monthly budget enforcement across many runs.
  • Provider retention, residency, encryption, and model-training terms.
  • Full DLP/privacy treatment of non-identifier fields and free text.
  • Capacity results at 6-7 million records on production infrastructure.
Decision posture: approve a controlled pilot and reference implementation, not unrestricted production deployment. The implementation demonstrates governance and economics; the pilot must validate real data shape, performance, quality, provider controls, and realized labor benefit.

04

Factory: what is generated and why

The factory converts a confirmed business specification into a complete project that a team can own, version, test, and operate independently.

Generated project contents

  • .github/agents/: orchestrator and mode-appropriate specialists.
  • .github/skills/: add dataset, define discrepancy, tune from review, investigate result.
  • config/: project, datasets, mappings, filters, comparison/diff, pipeline and guardrails.
  • rules/: priority-ordered known-discrepancy logic.
  • scripts/parity.py: unified operational CLI.
  • parity_core/: vendored engine for standalone reproducibility.
  • docs/: manual, analysis flow, confirmed requirements and prompts.
  • .parity-factory.json: factory and engine versions.

Generation controls

  • Validate project slug, supported mode and credential absence.
  • Render A, B or AB templates from the specification.
  • Copy the core engine so generated projects do not depend on the factory at runtime.
  • Write configuration and optional synthetic/sample data.
  • Optionally initialize Git.
  • Validate the generated project before returning success.
Ownership model: the factory is a reproducibility tool; the generated project is the deployable, independently maintained unit.

06

Agent model: coordinate, specialize, explain

Agents are not the data engine. They select the appropriate workflow, confirm prerequisites, interpret evidence, and delegate work to tested scripts.

Archon coordinator

Maintains task state, checks dependencies, retries failing commands, and exposes status/resume.

Data specialists

Loader, IMS migrator, CPP analyst and classifier understand source-specific evidence and operational gates.

Reasoning specialists

LLM analyst handles unresolved cases through validated JSON rather than direct database access.

Output specialists

Reporter and consolidated reporter generate business artifacts from persisted decisions.

Quality specialists

Validator reconciles counts, schema and workbook rows; review coordinator imports governed feedback.

Factory project designer

Clarifies requirements, confirms the specification, triggers generation, and runs the smoke test.

Terminology: the deck's "13 agents" is CPP-specific. The reusable factory emits 7-13 agents depending on configured mode and responsibilities.
07

LLM security and bounded usage

The LLM receives less data, sees pseudonymized identifiers, and cannot write directly to the canonical database or schema.

Current implemented controls

  • Only unresolved POTENTIAL_ISSUE or IMS_DATA_ISSUE records are selected.
  • Store, offering and deal identifiers are replaced with SHA-256-derived tokens.
  • Nested hypothesis/evidence references are scrubbed for consistency.
  • Maximum 500 candidates per run, 50 per batch, 20 batches.
  • Projected spend ceiling is $5.00 per run.
  • Returned classification is allow-listed and row existence is validated.

LLM_REDACTION_SALT

token = "h_" + first10(SHA256(salt + ":" + field + ":" + value))

The secret salt prevents easy dictionary matching of common identifiers. The demonstration currently permits an empty salt; production must set require_salt: true and inject a high-entropy secret from a vault.

PseudonymizationNot anonymization
Residual exposure: prices, dates, directions, row IDs and business context remain. Production requires provider-term approval, DLP/privacy review, retention/residency decisions, encryption, access control, and model-training restrictions.

LLM billing and 6-7 million record ROI

The economic model is deliberately transparent: it separates measured $0.00 pipeline cost, forecast external LLM cost, and realized business value.

ROI assumptions

6M cases/month, 8 manual minutes/case, $45 loaded hourly rate, 20% candidate rate, 70% acceptance, 2 residual review minutes, $0.001868/candidate LLM cost, and $250 fixed monthly cost.

Business interpretation

Gross value comes from reduced review time. It becomes cash ROI only when staffing, contractor spend, or demonstrable throughput gains are actually realized. Quality, rework and incident cost must be measured too.

Critical scale caveat: 500 candidates and $5 are per-run limits. They are not enterprise monthly limits. At 6M records, the estimate assumes approximately 2,400 governed runs. Production needs a central budget, rate/concurrency limit, priority queue, and kill switch.

10

Production readiness: approve the pilot, close the gaps

The implementation is a strong reference architecture and controlled demo. Production approval requires explicit ownership of the remaining governance and scale controls.

Before go-live

  • Require and rotate LLM_REDACTION_SALT through a secret manager.
  • Replace illustrative rates with approved provider contract prices.
  • Approve retention, residency, encryption and training-use terms.
  • Complete DLP/privacy review for remaining fields and free text.
  • Add provider identity/rate/budget enforcement and monthly kill switch.
  • Reconcile token estimates with provider receipts.
  • Run 6-7M volume, failover, concurrency and support simulations.
  • Measure accepted decisions, false acceptance, rework and realized labor value.

Already demonstrated

  • Confirmed-spec generation and standalone ownership.
  • Deterministic-first classification and controlled exception hand-off.
  • Redaction, spend projection, candidate and batch caps.
  • Validated findings and manual precedence.
  • Non-blocking audit/inspection markers with auto-resume.
  • Idempotent loading and migration behaviors.
  • Database-to-report reconciliation.
  • Reproducible deck, report and metric generation.
Recommended decision: fund a production pilot with a bounded dataset, contract-backed model, central budget controls and measurable reviewer outcomes. Do not market the 6M scenario as an invoice forecast or guaranteed saving until the pilot validates all assumptions.
