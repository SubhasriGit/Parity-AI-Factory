Launch the complete pipeline through one orchestrated instruction

One coordinator. Twelve governed steps. A single business instruction. The CPP PM000003 Orchestrator, represented as Archon in the architecture, translates the requested outcome into a dependency-ordered plan, verifies readiness, delegates to the appropriate specialists, and returns auditable evidence at completion.

Named-task execution validates only that task's prerequisites and avoids rebuilding earlier completed stages.

Resume a failed or interrupted run

Agent: CPP PM000003 Orchestrator

Type in chat: Resume pipeline

Use the CPP PM000003 Orchestrator to inspect state/task-state.json, identify the first failed, blocked, incomplete, or human-inspection-required task, explain the missing evidence, and resume only if its prerequisites are valid. Rerun no successful task unless necessary for the requested repair.

For a known task, say: “Resume ims-migrate only; do not replace any table without explicit approval; report the blocker or evidence.”

What the orchestrator needs from the user: run scope, database/output intent, relevant source paths when they are not already confirmed, and any explicit approval for replacement or refresh. It must not infer store/day mappings, overwrite permission, model behavior, or report layout.
Prerequisite gate: requirements-confirm is a documentation/configuration gate, not an executable data task. Full execution begins with database initialization only after the requirement state is confirmed.

Use the CPP PM000003 Orchestrator to resume only the failed ims-migrate task. Read its last attempt evidence, identify the root cause, ask for missing approval or mapping if needed, and retry only after the prerequisite defect is corrected. Do not silently refresh or replace tables.

From the middle

Agent selection guidance: use a specialist for one clearly owned operation; use the Orchestrator for full, resume, status, from-task-X, prerequisite checking, or coordination across multiple agents.
Independent does not mean ungoverned: missing requirements, a stale schema, absent day mapping, missing review workbook or invalid prerequisite state must produce a named blocker or clarification request. A specialist must not bypass those gates.

Is self-healing implemented?

Partly: the pipeline has retry and resumability controls, but not unrestricted autonomous repair.

  • Retry: a failed executable task is attempted again up to the configured two retries, meaning up to three total attempts.
  • Same safe command: retry repeats the mapped task command; it does not invent a new mapping, schema, rule, or destructive repair.
  • Evidence: every attempt stores duration, exit code and shortened output in state/task-state.json.
  • Exhaustion: failure after retries becomes HUMAN_INSPECTION_REQUIRED; the overall state records that inspection is needed.
  • Resume: the orchestrator can identify the first unresolved task and continue after the prerequisite problem is corrected or approved.
  • Human control: destructive refresh, replacement, missing mapping, ambiguous requirements and production credential decisions require explicit confirmation.
Accurate demo statement: “The system self-recovers from transient task failures through bounded retries and persistent resume, but it does not silently self-heal a bad mapping, corrupt data, missing requirement, or unsafe configuration. Those conditions are audited and escalated for human inspection.”
01

Confirm requirements

The project must not execute against unstated assumptions.

Owning agentCPP Requirements Analyst

Why: create the approved operating contract before any data work: project identity, datasets, keys, rules, review policy, outputs and exceptions.

How / who coordinates

The requirements analyst reads the confirmed requirements and current configuration, identifies open or contradictory points, asks focused questions, and records only explicitly approved decisions. Archon/the orchestrator treats this as the first prerequisite gate.

Script and execution

This is a documentation/configuration task, not a normal data-processing command. The current run_pipeline.py does not expose an executable requirements-confirm command; its status is prepared and represented through the task state.

Where results are stored

  • docs/CONFIRMED_REQUIREMENTS.md
  • config/cpp.yaml
  • Status/evidence in state/task-state.json

Passed to

Database initialization, CPP loading, IMS migration and mismatch-report parsing all require this gate. The recorded decisions become the source of truth for downstream configuration.

Demo wording: “No agent invents a missing business rule. The system asks, records the answer, and opens the implementation gate.”
02

Initialize the database

Create and verify the canonical evidence store.

Owning agentCPP Database Migrator

Why: all loading, classification, review and reporting need a consistent, versioned schema and indexed storage model.

Script

scripts/init_database.py --db <database>, invoked by scripts/run_pipeline.py.

How

Creates or idempotently verifies the schema from schema/001_create_core_schema.sql, sets the schema version and required indexes, and returns table/index counts.

Where updated

The SQLite database, including the core CPP, master, staging, mismatch and verdict tables. Schema evidence and command output are saved in state/task-state.json.

Passed to

CPP load, IMS migration and report parsing receive a valid database boundary. Later stages never need to invent their own storage.

Confirmed requirements→DDL/schema version→Indexed canonical DB
03

Load CPP snapshots

Bring five controlled CPP datasets into canonical tables.

Owning agentCPP CPP Loader

Why: the classifier and CPP analyst need authoritative corporate packet and reference evidence rather than reading production-shaped files ad hoc.

Script

scripts/load_cpp_snapshot_to_db.py --db <db> --csv-dir cpp_data, with optional --replace or --only.

How

Validates required files and columns, parses packet bodies, normalizes empty values, computes row hashes, batches inserts, records skipped/ignored/malformed counts, and supports idempotent reloading.

Where updated

cpp_price_packets, deal_price_master, regular_price_master, zone_store_relation and staging_product_price in SQLite. Load metrics go to command output and task state.

Passed to

Task 6 consumes the packet table for explosion. Task 7 queries the packet/master/staging evidence to evaluate KD rules.

Evidence: the synthetic run loaded 100 packet rows plus 300 deal, 100 regular, 5 zone and 300 staging rows.
04

Migrate IMS snapshots

Create store/day-specific IMS evidence inside the canonical database.

Owning agentCPP IMS Migrator

Why: deterministic classification needs the exact IMS state for a store and snapshot day, with an explicit provenance mapping.

Script

scripts/migrate_ims_snapshot_to_db.py --source <ims.db> --db <db> --day-map <map.json>, optionally with --refresh.

How

Reads explicit source-table/store/day mappings, validates four-digit stores and ISO dates, creates one mf_data_<store> table per store, inserts rows, and records deduplication, refresh and parity counts.

Where updated

Dynamic SQLite tables such as mf_data_5101 through mf_data_5505, with indexed product, deal, price type and snapshot-day evidence. Optional backups are written outside the repository's tracked artifacts.

Passed to

The classifier queries these tables as IMS-side evidence for effective-date, master-price and discrepancy decisions.

Never assume a day: a valid source table without an explicit approved day mapping is insufficient and must block this task.
05

Parse the mismatch report

Convert raw directional mismatch messages into normalized candidate rows.

Owning agentCPP Report Runner

Why: the classifier must work from structured keys, dates and prices rather than parsing log text repeatedly.

Script

pm000003_mismatch_report.py --config <config.json> --persist-to-db <db>, optionally filtered by analysis date.

How

Validates headers, applies the configured DTO regex, extracts store/product/deal/date/price values, normalizes timestamps, assigns price type and direction, accounts for malformed rows, and pairs directional records where possible.

Where updated

Structured rows are inserted into mismatch_input. Daily review workbooks are generated under the configured reports directory, and parse/persistence metrics are returned.

Passed to

The deterministic classifier consumes mismatch_input. The reporting stage later joins it to mismatch_verdict.

Evidence: 50 source messages produced 250 parsed DTO rows in the demonstration, with zero malformed rows.
06

Explode CPP packets

Transform nested packet JSON into queryable evidence rows.

Owning agentCPP CPP Analyst

Why: raw packet arrays are difficult and expensive for rule evaluation. One normalized row per price element makes evidence lookup deterministic and auditable.

Script

scripts/cpp_analyst.py --db <db>.

How

Reads validated packet bodies, parses nested regular, promo and core-charge values, normalizes price fields, detects invalid/truncated bodies, and rebuilds the analytical table idempotently.

Where updated

cpp_data in SQLite. The command returns inserted, malformed and type-level explosion metrics; executable evidence is recorded by the pipeline driver.

Passed to

The classifier uses cpp_data for CPP-side comparisons alongside IMS and master-data tables.

Evidence: the synthetic run exploded 100 packets into 200 normalized evidence rows.
07

Classify with deterministic KD rules

Establish the governed baseline before any AI review.

Owning agentCPP Classifier

Why: known discrepancy conditions should be decided reproducibly by ordered business rules, not inferred by a model. Only unresolved or ambiguous cases should require LLM assistance.

Script

scripts/classify_kd.py run --db <db> [--analysis-date <date>].

How

Loads each mismatch_input row, constructs paired and snapshot evidence, then applies the configured first-match KD priority. Each verdict includes classification, KD code, confidence, hypothesis, supporting evidence and missing evidence.

Where updated

One row per input is written to mismatch_verdict, linked by row_id. Enriched evidence is also available for report generation.

Passed to

Expected/known-discrepancy rows remain deterministic. POTENTIAL_ISSUE and IMS_DATA_ISSUE rows are selected by the LLM bridge.

Mismatch row→CPP + IMS evidence→First-match KD rule→Verdict
Decision priority: deterministic rules establish the baseline; AI may add supported findings but cannot silently rewrite an allowed schema.
08

Review unresolved candidates

Bound and explain the optional LLM second pass.

Owning agentCPP LLM Analyst

Why: deterministic rules can leave ambiguity. A constrained second pass can propose evidence, but its data exposure and projected spend must remain bounded.

Script

The task driver runs scripts/llm_bridge.py export --db <db> --output output/llm_candidates.json.

How

Joins mismatch_input to mismatch_verdict, selects unresolved classes, redacts configured identifiers, batches rows, estimates token cost and applies the 500 candidates / 50 rows / 20 batches / $5 per-run controls.

Where updated

output/llm_candidates.json and output/cost/llm_cost_estimate.json. No database mutation occurs during export.

Passed to

An external LLM analyst receives the controlled JSON and may return output/llm_findings.json. Supported findings can be imported by llm_bridge.py import; this is separate from the driver's export-only task.

Implementation boundary: the current driver does not call a model API. The synthetic full-run generator separately creates/imports findings for demonstration. A real deployment must add the external submission, provider authentication, rate controls and receipt capture explicitly.
09

Import optional human review

Apply governed manual judgment with attribution.

Owning agentCPP Review Coordinator

Why: operational experts remain accountable for disputed or insufficient-evidence decisions, and their rationale must be traceable.

Script

scripts/review_and_report.py review-import --db <db> --file <reviewed.xlsx> --final-output <final.xlsx>.

How

Reads reviewed rows from All_Results, validates the manual classification/KD fields, compares human and automated decisions, imports allowed values, records reviewer identity/timestamp/notes, and preserves disagreements.

Where updated

Manual precedence is persisted in mismatch_verdict. Disagreement and feedback detail are written to the review-feedback JSON path, and a final workbook can be regenerated.

Passed to

The final report reads the now-governed verdict. Reports expose review and confirmation columns so missing review is visible rather than silently treated as approval.

Declared-versus-actual prerequisite: pipeline.yaml declares llm-review; the driver implementation currently permits human review after successful classify. This should be aligned if external-LLM review is mandatory.
10

Generate the Excel report

Present one reconciled operational view to the business reviewer.

Owning agentCPP Reporter

Why: analysts need a usable workbook containing summary, classification, supporting evidence, exceptions and review status.

Script

scripts/review_and_report.py report --db <db> --output <workbook> --final.

How

Joins mismatch_input and mismatch_verdict, creates summary/coverage breakdowns, writes detailed and directional sheets, and marks confirmation/review states in report columns.

Where updated

The final Excel workbook under reports/, normally including Summary, Classification_Summary, Summary_detail, All_Results and directional worksheets.

Passed to

The validator reconciles the workbook against the canonical database. Consolidation can later consume explicitly named validated workbooks.

Non-blocking audit: insufficient evidence can create HUMAN_APPROVAL_REQUIRED while the report still completes and preserves the deterministic result.
11

Validate database and workbook counts

Prove that the report is a faithful representation of canonical state.

Owning agentCPP Validator

Why: a polished workbook is not sufficient unless its rows, required sheets and review fields reconcile to the database.

Script

scripts/validate_outputs.py --db <db> --workbook <final.xlsx>.

How

Reads the database and workbook without changing them, counts mismatch/verdict/result rows, verifies required sheets and review headers, compares workbook counts and detects problems.

Where updated

The script returns a validation JSON payload and exit code; the pipeline writes command evidence to state/task-state.json. Validation itself does not rewrite the business data.

Passed to

Successful validation releases the report for final consumption and is the prerequisite for optional consolidation. Failure is a hard evidence problem, not a cosmetic warning.

Evidence: the latest synthetic validation reported 250 mismatch, 250 verdict and 250 workbook rows.
12

Optionally consolidate outputs

Provide a multi-run management view without changing canonical evidence.

Owning agentCPP Consolidated Reporter

Why: a business owner may need a dated overview across explicitly approved runs, not only a single daily workbook.

Script

scripts/consolidated_report.py --report <file1> --report <file2> --output <consolidated.xlsx>, with optional date filters.

How

Reads only explicitly supplied validated reports, extracts their summary and result sheets, filters by date if requested, and aggregates daily totals and issue breakdowns.

Where updated

The consolidated Excel workbook, including overview, daily summary and issues-to-review sheets. Source reports remain unchanged.

Passed to

Final management reporting. The task is explicitly optional and must not be treated as a blocker for the normal daily workflow.

Control: the consolidator should not scan or mix folders implicitly. Report files must be explicitly supplied or approved by the user.

How all 12 tasks are tracked

One orchestration record connects commands, attempts and evidence.

CoordinatorArchon / CPP Orchestrator

Order and prerequisites

config/pipeline.yaml declares task IDs, owners, prerequisites and outputs. The orchestrator reads this configuration and validates what is ready.

Execution

scripts/run_pipeline.py maps executable task IDs to concrete commands, runs each with up to two retries, and supports full, task, status and resume modes.

State and evidence

state/task-state.json records status, command, attempts, timestamps, return codes and truncated stdout/stderr. This is execution evidence, not the canonical business database.

Agent versus script

The agent checks intent, prerequisites and evidence. The script performs deterministic data work. The final state is updated by the orchestrator after the command result.

Source: config/pipeline.yaml, scripts/run_pipeline.py, task-specific agents, scripts and generated artifacts.This explanation distinguishes implemented behavior from intended or production-only controls.
