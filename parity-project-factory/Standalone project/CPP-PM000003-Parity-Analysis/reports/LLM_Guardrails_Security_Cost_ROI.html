02

What the security control actually does

Before candidate JSON is exported, direct store, offering and deal identifiers are replaced with deterministic tokens. References to those values inside deterministic hypothesis and evidence text are also replaced.

STEP 1Database selection

Only unresolved classifications are selected.

STEP 2Identifier redaction

Store, offering and deal values become h_ tokens.

STEP 3Volume and spend caps

Rows are admitted only within batch and budget limits.

STEP 4Validated JSON hand-off

The boundary is file-based; no model SDK is invoked in this pipeline.

STEP 5Controlled return

Findings are validated; insufficient evidence preserves the deterministic verdict.

Minimized exposureOnly candidate records are exported, not all 250 rows.
Pseudonymized IDsOperational identifiers become stable, non-plain tokens.
Text consistencyMatching identifiers are also scrubbed from nested evidence.
Human accountabilityInsufficient evidence is audited and never treated as approval.
Security boundary, not a magic claim: this is pseudonymization, not complete anonymization. Prices, dates, directions, row IDs and business context remain. A person must still approve the data classification, provider terms, retention, residency, training-use restrictions and access controls. Sensitive free text needs a separate DLP/content-safety scan.
03

LLM_REDACTION_SALT explained for business

A salt is a secret extra value mixed into the identifier before hashing. It makes the resulting token harder to reverse by trying common store or deal numbers.

How the token is produced

token = "h_" + first10(SHA256( salt + ":" + fieldName + ":" + originalValue ))

Example shape: 0035 becomes h_b5667eceb7. The first 10 hexadecimal characters are displayed to keep the exported payload compact.

Why the salt matters

Without a salt: an attacker who knows the identifier space can hash likely values and compare outputs.

With a secret, rotated salt: that lookup table is no longer useful without the secret. Rotating it changes tokens, so use one approved salt for a run and retain mapping policy deliberately.

Current demo state: require_salt is false. The demo therefore continues if the environment variable is absent, using an empty salt. For production, set require_salt: true and provide a high-entropy secret through the secret manager, not a config file, command line or source control.

How the LLM bill is calculated

Providers normally bill input, cached input and output tokens separately per one million tokens. The pipeline estimates the payload before a model call and keeps that estimate separate from measured usage.

Estimated cost = [ (uncached input tokens × input price per 1M) + (cached input tokens × cached price per 1M) + (output tokens × output price per 1M) ] ÷ 1,000,000

Direct ROI

Hours avoided and staffing or contractor expense reduced. Use loaded labor rates and documented actual handling time.

Operational ROI

Faster exception triage, more consistent evidence capture, and a lower queue for scarce reviewers.

Risk-adjusted ROI

Measure false acceptance, rework, incident cost and audit effort. A low LLM bill is not valuable if residual quality risk is high.

Production go-live checklist

The control package is implementation-ready; production approval still requires ownership and evidence beyond this synthetic run.

Required before production

  • Set require_salt: true and inject LLM_REDACTION_SALT from a secret manager.
  • Replace illustrative prices with approved model and contract rates.
  • Approve provider data retention, residency, encryption and model-training terms.
  • Complete DLP/privacy review for non-identifier fields and free text.
  • Add hard API enforcement for rate, daily spend and identity policies; this repository calculates the hand-off estimate but does not call the provider.
  • Reconcile estimated tokens to provider receipts during a controlled pilot.

Already implemented

  • Only unresolved records are selected for candidate export.
  • Candidate, row-per-batch, batch-count and projected-spend caps.
  • Identifier and nested-text redaction.
  • Classification allow-list and row existence validation on import.
  • Insufficient evidence preserves the deterministic result.
  • Transparent estimate artifact, report metrics and 42-test coverage.
  • Human-approval audit does not block final reporting or automatic resume.
